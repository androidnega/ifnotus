# IFNOTUS UI PRIVILEGE & NAVIGATION AUDIT
## Show only the UI each role actually needs

Audit Date: August 28, 2026
Auditor Roles: Lead Product Architect, Lead IAM/RBAC Engineer, Lead Frontend Engineer, Lead Hosting Platform Architect, Lead UX Architect
Audit Scope: Frontend Router, Navigation Registries, Layouts, Sidebars, View Components, Action Buttons, Tab Interfaces & Plan Gating
Operating Mode: AUDIT ONLY (No code, route, permission, or infrastructure mutations performed)

================================================================================
1. EXECUTIVE CONCLUSION
================================================================================

The IFNOTUS access control architecture recently achieved strong backend permission partitioning (canonical 7-role IAM model, step-up authentication for web terminal, platform-owner filesystem storage root restriction, and CGNAT-safe throttles).

However, frontend UI navigation and view visibility still suffer from significant permission-coupling leaks and over-broad exposure:

1. Permission Re-use Leak (`customers:manage`):
   Both `/platform/orders` and `/platform/accounting` are guarded by `Permission.CUSTOMERS_MANAGE`. Consequently, `support_agent` (which requires `customers:manage` for customer lookups) can see company accounting summaries, daily cash collections, and payment ledgers.
2. Platform Admin Infrastructure Pollution:
   `platform_admin` receives `servers:read`, `system:read`, `files:read`, and `databases:read`, displaying infrastructure-level host navigation items (`/servers`, `/operations`, `/files`, `/databases`) that belong strictly to `platform_owner` or tenant-scoped operational engineers.
3. Missing Role-Specific Financial / Infrastructure Split:
   `billing_agent` should see orders and payment reconciliation queues, but the sidebar bundles Plans (`platform:write`) and generic host tools together.
4. Auditor Action Exposure:
   While `auditor` is strictly read-only, several view templates lack explicit `can(Permission.*_WRITE)` guards around action buttons (e.g. modals, restart buttons, trigger sync buttons, or download buttons), causing actionable UI elements to be rendered even when backend API calls would fail with 403.
5. Customer vs. Staff Portal Gating:
   Customer portal (`/hosting/:id`, `PortalSitePanel.vue`) has mature plan matrix checking (`envCan()`, `visibleStacks()`), but needs stricter alignment with actual server runtime capabilities so that plan limits (e.g., 0 mailboxes, 0 databases, disabled cron) hide whole tabs rather than rendering disabled forms.

Verdict: The UI requires a targeted frontend navigation refactor and fine-grained action-level conditional rendering across all 7 canonical roles.

5. PLATFORM OWNER UI
================================================================================

Role Purpose: Complete governance, infrastructure health, security oversight, disaster recovery, and staff access management.

Permitted Navigation:
- Overview (/panel)
- Customers (/platform/customers)
- Hosting Accounts (/hosting, /platform/customers)
- Orders & Billing (/platform/orders, /platform/accounting)
- Plans & Pricing (/platform/plans)
- Modern Applications (/applications)
- Domains & DNS (/domains)
- SSL Certificates (/ssl)
- Email Diagnostics (/admin/mail)
- Infrastructure:
  * Host Health (/servers)
  * Operations & Queues (/operations)
  * Security & Firewall (/security)
  * Emergency Terminal (/terminal - tucked away, warning banner)
- Settings & Staff Access (/settings)
- Support & Escalations (/support)

Risk & Governance Policy:
- Web Terminal: Must be labeled Emergency Terminal, visually separated from routine navigation, and always require fresh password confirmation on execution.
- Server File Root: Only `platform_owner` can access `/srv` and system roots.
- Staff Management: Only `platform_owner` can create or assign roles to other staff.
