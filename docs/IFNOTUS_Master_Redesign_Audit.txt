SHORT ANSWER
------------
YES — the Master Redesign plan phases 0 through 18 are complete in code
and have been deployed to the live server, plus one follow-on that made
the Hosting Panel a real day-to-day workspace (not just a shell).

NO — that does not mean every future hosting product idea is finished.
Some items are solid foundations (apps registry, multi-database table,
SSH password split, capacity gates) that still need deeper product polish
or ops work. Explicitly still OUT of scope / not finished as full product:
  - Real SFTP service (FTP remains; labelled honestly)
  - Off-site / disaster-recovery backups (same-VPS backup is not DR)
  - External Cloud VPS/VDS provider provisioning (packs blocked on shared node)
  - Full “buy → pay → provision → ACTIVE” production smoke checklist
    still has unchecked manual QA items (see phase 18 notes)

Preserved routes still work: /login, /signup, /account, /panel.


WHAT WAS DONE — BY PLAN PHASE (LAYMAN / PLAN LANGUAGE)
------------------------------------------------------

PHASE 0 — Baseline
  Mapped what already worked. Added regression tests so later redesign
  work would not silently break purchase, OTP, staff permissions, or
  package gates. No customer-facing redesign in this phase.
  Doc: docs/phase0-regression-baseline.md

PHASE 1 — Student zone
  New student / project sites use surnames under serverlabsttu.space.
  Old sites on *.ifnotus.space still recognized (no mass rename).
  Catalog meta, SSL/nginx helpers, DNS template updated.
  Live verified: catalog student_zone = serverlabsttu.space
  Migration: 0020_student_zone_serverlabsttu

PHASE 2 — Progressive onboarding
  Phone-first signup asks for name and email in steps instead of one
  heavy form. Checkout only allowed when required identity is complete.
  Migration: 0021 (customer progressive identity columns)

PHASE 3 — OTP / authentication hardening
  Production never returns the SMS code on the page when debug is off —
  including when SMS delivery fails.
  Request cooldown and rate limits on OTP endpoints.
  Production fails closed if the OTP store (Redis) is unavailable.
  Live verified: debug_code hidden on OTP request.

PHASE 4 — Entitlement model v2
  What a customer paid for is snapshotted with the subscription
  (SubscriptionEntitlementSnapshot), not only looked up live from the
  current plan row.
  Plan version field added. Environment API can expose entitlements.

PHASE 5 — Resource / capacity model
  Separate reserve percentages for CPU, RAM, and storage.
  Minimum free disk kept on the shared node before selling/setup.
  Shared storage target aligned toward 256 GB class sizing.
  Capacity admission used when picking a node for a plan.

PHASE 6 — Account vs Hosting Panel
  Account stays for overview / billing / settings.
  Manage Hosting opens /hosting/:environmentId for technical tools.
  Follow-on (after phase 18): panel embeds real site tools in place
  (files, apps, domains, email, FTP, backups, logs) via shared tooling
  composable — not redirect stubs.

PHASE 7 — Provisioning state machine
  Setup records step progress instead of jumping straight to “ready”.
  No silent “Docker failed → pretend filesystem is fine” when Docker
  was required.
  Required web (nginx) failure fails the job instead of marking ACTIVE.
  Environment stays provisioning until health gate allows ACTIVE.

PHASE 8 — Tenant Unix identity / filesystem boundaries
  Deterministic intended unix uid/gid per environment.
  Path join helper blocks “..” escape attempts.
  Ownership prefers tenant ids when present on the host; otherwise
  records intent for later ops.

PHASE 9 — SFTP / SSH redesign (partial product truth)
  FTP labelled as FTP (not falsely as SFTP).
  Note that SFTP is still coming for entitled plans.
  SSH can use a password separate from FTP (not forced to share).
  Real SFTP daemon / preferred protocol switch: NOT done yet.

PHASE 10 — Application runtime manager (foundation)
  application_instances table and customer API stubs to list/create
  managed app records with entitlement checks.
  One-click stacks (static / WordPress / Laravel / Node) still the
  main installers; registry is the foundation for fuller runtime mgmt.

PHASE 11 — Database service v2 (foundation)
  environment_databases table + list API (including legacy single
  db_* slot as synthetic). Multi-DB product UX still early.

PHASE 12 — Domains / DNS / SSL v2
  Clearer customer domain lifecycle status
  (e.g. pending_verification / active / failed / detached).
  SSL display prefers reading real certificate dates where possible.

PHASE 13 — Email service boundaries
  Mailbox create respects package mailbox limits / capabilities.

PHASE 14 — Backups
  Environment backup metadata and retention tied to entitlements.
  Documented clearly: same-VPS backup is NOT disaster recovery.
  Doc: docs/phase14-backups.md

PHASE 15 — Staff capacity UI
  Staff capacity screen at /platform/capacity (API backed).

PHASE 16 — Monitoring / abuse / protection
  Disk pressure evaluation; critical disk can block new provisioning.
  Stub / foundation for automated protection — not a full SOC suite.

PHASE 17 — Package catalog rebuild (shared-node honesty)
  Cloud VPS / VDS packs not sellable on the shared node.
  Calmer marketing copy for large shared packs.
  Plan matrix remains the capability authority.

PHASE 18 — Release / migration / scale-out readiness
  Migration and rollback notes, Shared Node 02 ops howto, remote
  backup / VPS-provider future notes, route compatibility list.
  Doc: docs/phase18-release-readiness.md
  Doc: docs/redesign-phases-complete.md
