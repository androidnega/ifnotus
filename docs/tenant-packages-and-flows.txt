================================================================================
1. ACCOUNT vs HOSTING (TENANCY MODEL)
================================================================================

ONE CUSTOMER ACCOUNT (identity + billing)
  - Register with phone OTP (no hosting required).
  - Complete profile later: real name, email, optional password.
  - Owns: Orders (invoices), Subscriptions, Environments, Domains, AI credits,
    Support tickets.

MANY HOSTING PURCHASES UNDER THAT ACCOUNT
  - Each paid hosting order → 1 Subscription → 1 CustomerEnvironment (site jail).
  - Tools (files, stack, DB, FTP, DNS, mail) are always scoped to one environment.
  - Dashboard API returns all non-terminated environments for the customer.

RELATIONSHIP
  User (login) 1:1 Customer
    ├─* Order          (checkout / MoMo invoice)
    ├─* Subscription   (paid entitlement + plan limits)
    │     └─* CustomerEnvironment  (document root, domain, FTP, optional DB)
    ├─* CustomerDomain
    └─1 AiCreditAccount (wallet on the account, not per site)


================================================================================
2. END-TO-END CUSTOMER PROCESS
================================================================================

A. REGISTER / LOGIN
  1. Phone number → request OTP (SMS; debug code if SMS not configured).
  2. Verify OTP → creates Customer + User if new
     (placeholder email like p…@phone.pending.ifnotus, name "Customer").
  3. Complete profile (required before creating an order):
     full name, real email, optional company/password.
  4. Land on /account (customer portal).

  Staff use /login with email/password (+ optional TOTP). Customers are steered
  toward phone signup. Separate staff panel: /panel.

B. BUY HOSTING (NEW ORDER)
  1. Billing → "New order" → /account/plans
     (or marketing Plans → signup with ?plan= then checkout).
  2. Pick a pack (managed plans sellable on the shared node; Cloud VPS/VDS are
     catalogued but not sold off the shared disk — need their own VM).
  3. Domain choice during checkout:
     - register   = buy/attach a new domain
     - own        = customer already owns a domain
     - student    = free *.ifnotus.space hostname from surname
                  (surname.ifnotus.space, then surname1, surname2, …)
  4. Create order → invoice (short ref e.g. IFFCEA) → MoMo pay instructions.
  5. Customer submits MoMo transaction ID → payment_status = submitted.
  6. Staff confirms payment → activates hosting.

C. ACTIVATION / PROVISIONING
  On confirm_payment for a hosting order:
  1. Create Subscription (plan CPU/RAM/disk/bandwidth/AI credits allocated).
  2. Top up AI credits for the month onto the customer wallet.
  3. Enqueue provision job.
  4. ProvisioningEngine:
     - Pick infrastructure node for plan capacity.
     - Create document root under customer_environments_root.
     - Isolation: filesystem jail by default; Docker only if plan includes docker
       and isolation prefers docker (falls back to filesystem if start fails).
     - Create Domain + nginx (+ Let's Encrypt for *.ifnotus.space).
     - Create CustomerEnvironment (status active, limits from plan).
     - NO database by default.
     - Ensure FTP/SFTP account if pack includes sftp.
     - DNS A record; attach custom domain if purchased; queue SSL for custom.
     - Notify customer (email/SMS): hosting ready → open /account.

D. AFTER GO-LIVE — DASHBOARD
  Until a live environment exists:
    - Nav: Overview + Billing (Site hidden).
    - Overview empty state → finish payment / New order.

  After activation:
    - Overview: active site hero (domain, disk, health) + shortcuts.
    - Site panel unlocked (cPanel-style tools for the selected environment).
    - Billing: subscriptions, invoices, AI credits, New order (another pack).
    - Multi-env: weak pill switcher today; product direction is Services list →
      click one hosting → open that site’s panel.

E. RENEWAL / EXTRA PURCHASES
  - New order from Billing adds another subscription/environment under same account.
  - Renew / change-plan exist per subscription in Billing UI.
  - Cancelled/disputed invoices are hidden from the customer invoice list.

5. STACKS — WHAT THEY ARE AND HOW TENANTS USE THEM
================================================================================

TWO LAYERS

A) MATRIX STACKS (entitlement)
   Declared per pack in plan_matrix (php, laravel, wordpress, mysql, python,
   django, fastapi, flask, nodejs, nextjs, express, react, vue, postgres,
   mongodb, redis, docker).
   UI lists included/limited stacks for the pack. "no" stacks are hidden.

B) ONE-CLICK INSTALLERS (implemented today)
   Ids: static | wordpress | laravel | nodejs
   Mapped to matrix keys: static→php, wordpress→wordpress, laravel→laravel,
   nodejs→nodejs.
   Student Starter only sees one-click options that pass matrix (static always
   allowed; WordPress/Laravel/Node if pack allows).
   Higher packs also LIST matrix stacks (Python, Django, …) with
   one_click=false — "Deploy via Files or Git (one-click coming soon)".

INSTALL FLOW (customer Site → Stack)
  1. Pick stack → Install (blocked if one_click=false).
  2. Background job with step progress (prepare → … → done).
  3. Writes into environment document_root; updates nginx as needed.
  4. WordPress / Laravel: create MySQL DB + credentials on the environment.
  5. Node: Express starter + npm + reverse proxy.
  6. Static: starter PHP/HTML page, no DB until needed.
  7. Customer can Clear install (optionally drop database) and reinstall.

STACK STEPS (summary)
  static:     prepare → files → nginx → done
  wordpress:  prepare → database → download → extract → config → nginx → done
  laravel:    prepare → database → composer → env → nginx → done
  nodejs:     prepare → files → npm → start → nginx → done

DEFAULT DB ENGINE FOR PACK
  MySQL if mysql stack allowed; else PostgreSQL if postgres allowed; else none.
  Provisioning itself does NOT create a DB — only stack install (or staff) does.

6. DATABASE — HOW TENANTS ACCESS IT
================================================================================

WHEN A DB EXISTS
  - After WordPress or Laravel one-click (MySQL created and bound to env).
  - Fields on CustomerEnvironment: db_engine, db_name, db_username, db_host,
    db_port, db_password_encrypted, db_registry_id.
  - Default host shown to customers may be masked/normalized for safety.

ACCESS PATHS

1) Site → Database tab
   - Shows engine, name, username, host, port.
   - Reveal password / connection URI (reveal=true API).
   - Browse schema / tables.
   - Open SQL Studio: /account/database/studio?env=<environment_id>

2) Database Studio (full UI)
   - Schema, rows, insert/update/delete, run queries.
   - WRITE operations require pack db_manage == "yes".
   - If db_manage == "limited" (e.g. Personal): browse OK; changing data denied
     with message to upgrade.

3) App config
   - WordPress: wp-config.php written with DB credentials.
   - Laravel: .env configured with DB credentials.

4) External clients
   - Use revealed host/port/user/password (subject to firewall / bind rules on
     the server). Not all packs expose remote MySQL the same way; panel studio
     is the primary supported path.

NO DATABASE YET
  API returns: "No database on this site yet. Install WordPress or Laravel,
  or ask support to attach one."

7. FILES, FTP, SSH, DNS, MAIL (PER ENVIRONMENT)
================================================================================

FILES
  - Capability: file_manager (almost all packs yes).
  - In-panel browser + full /account/files?env= window.
  - Uploads count against storage_limit_gb; write blocked when over quota.

FTP / SFTP
  - Capability: sftp.
  - ensure_account creates jailed user with home = document_root.
  - Credentials shown in Site → FTP tab.

SSH
  - Modes: no / limited / jail / root (VPS/VDS).
  - ensure SSH endpoints exist; Personal has ssh=no.

DNS / SSL / CUSTOM DOMAINS
  - Student hostnames live under ifnotus.space (wildcard-friendly).
  - Custom domains: attach + NS instructions; SSL queued when ready.
  - custom_domains limit enforced per pack matrix.
  - Preview/staging hostnames gated by pack preview/staging flags.

CRON / GIT / LOGS / REDIRECTS
  - Cron, git clone/pull, logs, redirects APIs under /customers/environments/{id}/…
  - Feature levels can be limited or no per pack.

MAIL
  - Create mailboxes under environment domain up to pack mailboxes limit.

12. HOSTING SUPER ADMIN / STAFF PANEL — STRUCTURE & CAPABILITIES
================================================================================

OVERVIEW
  The staff console is the WHM-style host control panel at /panel (meta.panel =
  "staff"). It has two layers:

  A) HOST CONTROL  — manage the shared Contabo server itself
     (websites discovery, DNS, files, DBs, mail, SSL, backups, firewall,
      monitoring, terminal, Docker).

  B) ACCOUNTS (product platform) — manage IFNOTUS customers, plans, MoMo
     orders, support tickets, and per-tenant environment remediation.

  Pure customers (role "customer" only) are blocked from all staff routes.
  Staff may open /account if they also have a customer profile; otherwise
  they stay in /panel.


--------------------------------------------------------------------------------
12.1 ACCESS & AUTH
--------------------------------------------------------------------------------

  URL:     https://ifnotus.space/login  → after auth → /panel
  Auth:    email + password
  Extra:   device challenge / TOTP where configured
  Layout:  DashboardLayout + AppSidebar (control-ui theme)

  API prefix for product console: /api/v1/platform/... (platform_admin.py)
  Host tools use their own routers (domains, files, mail, security, etc.).


--------------------------------------------------------------------------------
12.2 STAFF ROLES (who can do what)
--------------------------------------------------------------------------------

  Role            Primary job
  --------------  ------------------------------------------------------------
  superadmin      Full control — staff accounts, terminal, privilege switch,
                  terminate sites, every permission
  admin           Business — plans, billing confirm, customers, env remediation;
                  NO host shell / files write emphasis
  operator        Hands-on hosting — domains, mail, files, databases, env ops;
                  NO plan CRUD / billing confirm
  customer_care   MoMo confirm + support tickets only (no env/hosting edits)
  viewer          Read-only across the staff panel
  customer        Portal only — empty staff permission set

  Permission families (backend Permission enum):
    system:*, servers:*, deployments:*, apps:*, domains:*, ssl:*, files:*,
    mail:*, terminal:execute, databases:*, monitoring:*, users:*,
    support:*, customers:manage, platform:read, platform:write, platform:ops

  Notable gates:
    platform:write     → create/edit plans, integrations, site theme
    platform:ops       → suspend/restore env, health, stacks, repair FS,
                         grant AI credits
    customers:manage   → confirm / reject MoMo, retry provision
    system:admin       → terminate env, create/update staff users,
                         provision hosting for a customer, security page
    terminal:execute   → Terminal / SSH (superadmin-heavy)

  Superadmin can temporarily "work as" admin | operator | viewer |
  customer_care (privilege switch) — never as customer or another superadmin.

--------------------------------------------------------------------------------
12.4 CONTROL — WHAT EACH HOST SCREEN DOES
--------------------------------------------------------------------------------

  DASHBOARD (/panel)
    Host overview: resource gauges, health, traffic hints, SSH/terminal
    shortcuts, recent alerts/services. Operator view of the shared node —
    not a single customer’s site.

  WEBSITES (/applications)
    Discovered / registered apps on the host (nginx/sites style inventory).
    Detail page for metrics, logs, SSL, services, deploy-related actions.

  DNS (/domains)
    Server-wide domain & nginx site management (staff scope — all domains on
    the host, not tenant-jailed).

  FILE MANAGER (/files)
    Host filesystem browser/editor/upload. Staff sees broader roots than
    customers (customers are locked to their environment document_root).

  DATABASES (/databases + /databases/studio)
    Host DB registry + SQL studio for any managed DB on the node.
    Parallel to customer studio, but not limited to one tenant env.

  EMAIL (/admin/mail)
    Mail domains / mailboxes administration on the host.

  SSL (/ssl)
    Certificate discovery, issue, renew for host domains.

  BACKUPS (/operations)
    Host/ops backup and related operations actions.

  FIREWALL / SECURITY (/security) — system:admin
    Firewall and security controls for the host.

  MONITORING (/monitoring)
    Service health, metrics, collectors for the shared node.

  TERMINAL / SSH (/terminal, /terminal/full) — terminal:execute
    Key-based shell into the host. Intended for superadmin/ops — not exposed
    to customers.

  DOCKER / HOST (/servers)
    Container / host inventory and server management views.


--------------------------------------------------------------------------------
12.5 ACCOUNTS — PRODUCT CONSOLE (CUSTOMERS / PLANS / ORDERS / SUPPORT)
--------------------------------------------------------------------------------

  CUSTOMERS (/platform/customers) — PlatformCustomersView
    List/search customers (name, email, phone).
    Open customer detail:
      - Profile, AI credit balance
      - Subscriptions + orders summary
      - Environments list (domain, status, stack, DB chip, document_root)
      - Env sub-panels: Overview | Health | Stacks | Logs | Activity (audit)
    Actions (permission-gated):
      - Grant AI credits          (platform:ops)
      - Staff-provision hosting   (system:admin) — create paid-style provision
        for a customer with plan + domain without MoMo flow
      - Per environment:
          Health check, view usage (disk soft/hard)
          Suspend / Restore       (platform:ops)
          Terminate               (system:admin only — permanent)
          Clear stack (± drop DB) (platform:ops)
          Install stack           (platform:ops)
          Repair filesystem / WP FS_METHOD (platform:ops)
          Read env logs           (platform:ops)

  PLANS (/platform/plans) — PlatformPlansView
    List all hosting_plans (incl. inactive).
    Create / edit: name, slug, price monthly/yearly, CPU, RAM, storage,
      bandwidth, AI credits, custom_domains override, active flag.
    Option: auto-size resources from monthly price (₵30→0.25/256MB anchors).
    Bulk: "Rebalance from price" recalculates all plans’ resources.
    Hide/activate plan for public catalog.
    Requires platform:write for mutations.

  ORDERS (/platform/orders) — PlatformOrdersView
    Filter by payment_status (default: submitted / awaiting confirmation).
    Per order: customer link, plan, domain, MoMo txn id, invoice totals.
    Actions (customers:manage):
      - Confirm payment (amount received + staff note) → activates hosting
        (Subscription + provision job)
      - Reject payment → mark failed
      - Retry provision if paid but env not active

  SUPPORT (/support) — SupportTicketsView
    Staff inbox for customer tickets (support:read / support:write).
    Tickets may reference an environment_id when opened from a site context.

--------------------------------------------------------------------------------
12.8 DAY-TO-DAY SUPER ADMIN WORKFLOWS
--------------------------------------------------------------------------------

  1. MoMo activation
     Orders → filter "submitted" → verify txn in MoMo app → Confirm
     → subscription created → provision job → customer notified → site live.

  2. Broken customer site
     Customers → select customer → select env → Health / Logs →
     Repair FS or Clear stack / reinstall → Suspend if threatening host.

  3. Pack catalog change
     Plans → edit price/resources or Rebalance from price → Hide/Activate.

  4. Manual credit top-up
     Customers → Grant AI credits (ops).

  5. Comp / internal hosting
     Customers → Provision hosting (superadmin) with plan + domain.

  6. Hire staff
     Settings → create operator / admin / customer_care account.

  7. Kill a fraudulent site
     Customers → env → Terminate (superadmin only; irreversible from portal).


--------------------------------------------------------------------------------
12.9 WHAT SUPER ADMIN IS NOT
--------------------------------------------------------------------------------

  - Not the customer /account portal (that is phone-first client area).
  - Not a separate login per hosting package — staff remediate by picking
    the customer’s environment inside Customers.
  - Cloud VPS/VDS sales on this shared node are blocked in product logic;
    those need their own VM path even though plans exist in the catalog.
