1. EXECUTIVE CONCLUSION
----------------------------------------------------------------------------------------------------
The IFNOTUS codebase has undergone substantial hardening and architectural maturation through Phases
A through Y. The platform features a clean separation between billing, application runtime, and hosting
engines, backed by a pluggable `HostingProvider` abstraction and ISPConfig 3 integration.

However, from the perspective of an enterprise-grade, multi-tenant SaaS hosting provider, several
critical architectural boundaries require explicit formalization:
1. Role Model Clarity: The role names `admin` and `operator` blur the boundary between business administration
   (billing, plans, customer accounts) and technical hosting operations (domains, mail, DNS, databases).
2. Identity Boundary Enforcement: While customer endpoints are strictly sandboxed via `TenantService`,
   staff file management (`/files`) and staff terminal (`/terminal`) historically provided broad host-level
   access which must be strictly walled off from application-level roles.
3. Path & URL Consistency: Customer URLs currently expose UUIDs (`/hosting/:environmentId`) which should
   be streamlined into uniform, human-readable account/site slugs (`/account/hosting/:domain`).
4. ISPConfig Remoting Pipeline: The HostingProvider layer is cleanly decoupled in code, with 100% of
   customer panel actions now coordinator-routed through `CustomerPanelProviderService`.

Overall Platform Verdict: PASS on technical implementation; PROCEED WITH FORMAL REFACTORING SPECIFICATION.

4. CURRENT ROLE PROBLEMS
----------------------------------------------------------------------------------------------------
1. Ambiguity between `admin` vs `operator`:
   - `admin` currently holds `servers:delete` and `apps:write` but cannot manage domains/files directly.
   - `operator` has `servers:write` and `deployments:execute` but cannot manage customers or plans.
   - This leads to confusion on whether `admin` is a business manager or technical lead.
2. Super Admin Breadth vs System Safety:
   - `superadmin` has raw `terminal:execute` permission. While needed for emergency diagnostics,
     web-based root shell access presents a high-value attack surface if session cookies are intercepted.
3. Lack of Dedicated Billing Role:
   - `customer_care` currently confirms manual MoMo payments, but cannot issue refunds, adjust plan
     pricing, or inspect complete financial ledgers. A formal `billing_agent` role is missing.


----------------------------------------------------------------------------------------------------
5. RECOMMENDED FINAL ROLE MODEL
----------------------------------------------------------------------------------------------------
1. `platform_owner` (Super Admin):
   - Scope: Staff account creation/revocation, provider API credentials, emergency disaster recovery,
     destructive environment terminations, security policy and 2FA enforcement.
2. `platform_admin`:
   - Scope: Commercial plan catalog, coupon campaigns, customer management, high-level business metrics.
3. `hosting_operator`:
   - Scope: Technical hosting provisioning, domain DNS management, SSL certificate issues, mailbox
     remediation, database status, app runtime health, resource slice inspection.
4. `billing_agent`:
   - Scope: Payment verification (MoMo/Paystack), invoice adjustments, subscription term management.
5. `support_agent` (Customer Care):
   - Scope: Ticket read/reply, customer profile lookup, customer password reset assistance.
6. `auditor` (Viewer):
   - Scope: Read-only observation across dashboard, monitoring, audit logs, and compliance.
7. `customer`:
   - Scope: Self-service management of subscribed hosting environments, files, DBs, mail, and apps.

8. PRIVILEGES TO REMOVE / DEPRECATE
----------------------------------------------------------------------------------------------------
1. `terminal:execute` for general staff:
   - Web terminal should never be accessible to `operator`, `admin`, or `viewer`.
   - Accessible only to `platform_owner` with mandatory TOTP confirmation and strict command allowlisting.
2. `files:write` across `/srv` or `/var/www`:
   - Staff should never have an unrestricted web-based arbitrary file editor pointing to server root directories.
   - Tenant file operations must always be explicitly bound to the specific customer environment document root.


----------------------------------------------------------------------------------------------------
9. PRIVILEGES TO RESTRICT
----------------------------------------------------------------------------------------------------
1. `hosting.terminate`: Restricted strictly to `platform_owner` with `confirm=true` query gate and audit log.
2. `providers.manage` / `integrations.manage`: Restricted strictly to `platform_owner`.
3. `billing.manage` / `accounting`: Restricted to `platform_owner`, `platform_admin`, and `billing_agent`.


----------------------------------------------------------------------------------------------------
10. PRIVILEGES TO ADD
----------------------------------------------------------------------------------------------------
1. `billing.manage`: Dedicated permission for processing manual MoMo payments, refunds, and invoice overrides.
2. `disaster_recovery.execute`: Explicit permission for initiating offsite backups and automated restore drills.
3. `providers.manage`: Explicit permission for updating ISPConfig/payment gateway API secrets.

11. CUSTOMER / TENANT TERMINOLOGY CLEANUP
----------------------------------------------------------------------------------------------------
Standardized Hierarchy:
- **Customer**: The human or company account holder (`customers` table).
- **Subscription**: The active entitlement linked to a specific plan and billing cycle (`subscriptions` table).
- **Hosting Account / Environment**: The provisioned container/vhost space (`customer_environments` table).
- **Websites / Domains / DBs / Mailboxes**: Individual resource entities provisioned inside the environment.
- **Client (Internal)**: ISPConfig 3 system client record (`client_id`). Never exposed to customer UI.

14. /CPANEL & /MAIL ACCESS PIPELINE
----------------------------------------------------------------------------------------------------
1. `/cpanel` URL Workflow:
   - Rule: `https://<customer-domain>/cpanel` -> Nginx proxies or redirects to `https://ifnotus.space/go/hosting?host=$host`.
   - Security: Sanitized via `sanitize_panel_hostname` in `backend/app/services/platform/host_routing.py`
     to prevent open redirect vulnerabilities and host spoofing.
   - SSO: Authenticates customer session, resolves `CustomerEnvironment.domain == host`, and loads the panel.
2. `/mail` URL Workflow:
   - Rule: `https://<customer-domain>/mail` -> Nginx proxies to shared Roundcube webmail instance (`https://mail.ifnotus.space`).
   - Native Clients: IMAP/SMTP host `mail.<customer-domain>` configured with SSL SNI certificate.

16. END-TO-END PROVISIONING PIPELINE
----------------------------------------------------------------------------------------------------
```text
Customer selects plan
        ↓
Order created (status=pending)
        ↓
Payment verified (Paystack webhook or MoMo confirmation)
        ↓
Subscription activated
        ↓
Provisioning Task dispatched (Redis / Celery / asyncio worker)
        ↓
HostingProvider (Factory resolves ISPConfigHostingProvider)
        ↓
ISPConfig Remote API Client
        ↓
1. client_add(username, email, password, template_id)
2. sites_web_domain_add(domain, php_version, quota)
3. sites_database_user_add + sites_database_add (if plan includes DB)
4. mail_domain_add + mail_user_add (if plan includes mail)
5. sites_ftp_user_add + sites_shell_user_add
6. sites_web_domain_update(ssl_letsencrypt='y')
        ↓
Host Verification & Health Probe (HTTP 200, Nginx vhost active)
        ↓
CustomerEnvironment.status = 'active', provider = 'ispconfig'
        ↓
Customer accesses panel via https://domain/cpanel
```

17. DESTRUCTIVE ACTION POLICY
----------------------------------------------------------------------------------------------------
The following operations require mandatory protection:
1. `Terminate Customer Environment`: Superadmin only (`Permission.SYSTEM_ADMIN`), explicit `confirm=true` query parameter, writes audit log.
2. `Delete Database`: Requires password confirmation when invoked from Database Studio (`confirm_password`), audit log emitted.
3. `Clear Security / Terminal Logs`: Requires password confirmation (`confirm_password`).
4. `Customer Account Deletion`: Requires explicit confirmation and marks status as `deleted`.

18. RECOMMENDATIONS FOR UPCOMING REMEDIATION PROMPT
----------------------------------------------------------------------------------------------------
1. **Role Refactor**: Transition from the current 6 roles (`superadmin`, `admin`, `operator`, `viewer`, `customer_care`, `customer`)
   to the clean 7-role capability model (`platform_owner`, `platform_admin`, `hosting_operator`, `billing_agent`, `support_agent`, `auditor`, `customer`).
2. **Web Terminal Hardening**: Guard `/terminal` strictly behind `platform_owner` role, mandatory 2FA TOTP prompt, and explicit session timeout.
3. **Staff Storage Isolation**: Deprecate host-wide `/srv` and `/var/www` browsing in `FileManagerService` for standard staff roles;
   enforce environment-scoped file operations.
4. **URL Cleanup**: Standardize customer panel routes to `/account/hosting/:hostingSlug` for improved user experience.
