1. EXECUTIVE CONCLUSION
====================================================================================================
The IFNOTUS authentication architecture has a solid foundation with clear security separation between
external customer accounts, internal staff accounts, mailbox identities (Dovecot virtual users), and
underlying hosting control plane (ISPConfig Remote API).

Key Architectural Strengths:
1. ISPConfig Remote API is completely unexposed to end-users (0% browser exposure).
2. Customer `/cpanel` redirects validate hostnames through `sanitize_panel_hostname()` and route to
   internal SSO (`/go/hosting`) without trusting arbitrary Host headers.
3. Password domains (IFNOTUS User, Panel Password, Mailbox, DB, SFTP, ISPConfig, Linux root) are
   strictly isolated with independent hashes.
4. Staff 2FA enforcement via RFC 6238 TOTP is actively implemented for infrastructure roles.

Primary Security & Operational Gaps Identified for Remediation:
1. Browser Token Storage: JWT access and refresh tokens are stored in `localStorage`, creating XSS
   exposure. Migration to HttpOnly, SameSite=Lax/Strict cookies with CSRF tokens is required.
2. Refresh Token Family Tracking: Refresh tokens lack token family tracking and reuse detection;
   backend logout does not blacklist refresh token JTIs in a central revocation store.
3. Shared-IP Lockout (CGNAT Risk): `CONSECUTIVE_FAIL_LIMIT = 3` with `AUTO_UNLOCK_HOURS = 72` locks
   IPs at the network layer, which is dangerous on Ghanaian mobile networks (MTN, Telecel, AT) and
   shared campus/office NATs. A hybrid account + IP rate-limiting policy is necessary.
4. Staff Password Reset: Currently shares the public email token flow; privileged roles require
   mandatory MFA re-verification and immediate session revocation upon reset.

Verdict: AUDIT COMPLETE — GO FOR PHASED AUTHENTICATION REMEDIATION.

   - Port 8080 restricted to loopback/private firewall.
   - Internal authenticated communication strictly via `ISPConfigClient` REST/SOAP API.
6. Server Infrastructure (SSH/SFTP):
   - Port 22 SSH keys / isolated Linux unix users (`u_<tenant>`).

4. CURRENT AUTH API ENDPOINTS
====================================================================================================
1. Staff Auth (`backend/app/routers/v1/auth.py`):
   - `POST /api/v1/auth/login`: Authenticates staff credentials, triggers TOTP challenge if enrolled.
   - `POST /api/v1/auth/refresh`: Issues fresh access token from refresh token.
   - `POST /api/v1/auth/verify-device`: Approves new IP challenge.
   - `POST /api/v1/auth/confirm-password`: Step-up verification for sensitive operations.
   - `POST /api/v1/auth/totp/setup`: Generates RFC 6238 secret & QR code uri.
   - `POST /api/v1/auth/totp/confirm`: Activates TOTP after validating first code.
   - `POST /api/v1/auth/totp/disable`: Deactivates TOTP (requires password).
   - `POST /api/v1/auth/privilege-switch`: Allows platform owner to assume restricted role.
   - `POST /api/v1/auth/privilege-restore`: Restores platform owner token.
   - `GET /api/v1/auth/me`: Returns current user session context & permissions.

2. Customer Auth (`backend/app/routers/v1/customers.py`):
   - `POST /api/v1/customers/login`: Customer email/password login.
   - `POST /api/v1/customers/register`: New customer onboarding.
   - `POST /api/v1/customers/phone-otp/start`: Sends 6-digit SMS OTP via Redis/file storage.
   - `POST /api/v1/customers/phone-otp/verify`: Validates OTP and issues customer JWT pair.
   - `POST /api/v1/customers/panel/login`: Authenticates hosting-panel password.
   - `POST /api/v1/customers/panel/create-password`: Generates dedicated panel password.
   - `GET /api/v1/customers/panel/status`: Checks if hosting username/password exists.

5. CUSTOMER AUTH MODEL
====================================================================================================
- Primary Auth: Phone OTP (Ghana mobile numbers +233) OR Email + Password.
- Secondary / Recovery: Email verification links and password reset tokens.
- Panel Auth: Separate hosting-panel password (`PanelPasswordService`).
- Evaluation of Separate Hosting Password:
  * Decision: **TEMPORARILY RETAIN -> PLAN DEPRECATION IN FAVOR OF UNIFIED SSO**.
  * Reason: Maintaining separate passwords for IFNOTUS account and hosting panel creates password
    desynchronization, duplicate reset requests, and customer confusion. The unified SSO flow via
    `/go/hosting` is the superior long-term design.

====================================================================================================
6. STAFF AUTH MODEL
====================================================================================================
- Surface: Single canonical surface at `/staff/login`.
- Authentication Mechanism: Email/Username + Password + Mandatory RFC 6238 TOTP for privileged roles.
- Server-Side Role/Permission Routing:
  * All staff authenticate through the unified `AuthService.login()`.
  * After login, `permissions_for_roles()` evaluates real-time capabilities.
  * No separate login routes exist per role (clean single surface architecture).

====================================================================================================
7. PLATFORM-OWNER AUTH MODEL
====================================================================================================
- Required Factors:
  1. Primary Password (minimum 12 characters).
  2. Mandatory TOTP (RFC 6238 6-digit authenticator code).
  3. Step-up password re-authentication for destructive actions (e.g. `POST /api/v1/terminal/execute`,
     `DELETE /api/v1/platform/customers/:id`, database drop/purge).
- Privilege Switching:
  * Enabled exclusively for `platform_owner` / `superadmin`.
  * Allows temporary downgrade to test restricted view (e.g., `auditor`, `hosting_operator`).
  * Emits security audit log on switch and restore.

====================================================================================================
8. HOSTING-PANEL AUTH MODEL
====================================================================================================
- Flow:
  1. Customer visits `customer-domain.tld/cpanel`.
  2. Nginx maps request to `/api/v1/public/panel-redirect?host=customer-domain.tld`.
  3. `sanitize_panel_hostname()` validates hostname against DNS regex and reserved blocklist.
  4. 302 Redirect to `https://ifnotus.space/go/hosting?host=customer-domain.tld`.
  5. If authenticated, resolves environment via `TenantService.require_for_user()` ensuring IDOR safety.
  6. If not authenticated, redirects to `/login?redirect=...` preserving context.

====================================================================================================
9. WEBMAIL AUTH MODEL
====================================================================================================
- Flow: `customer-domain.tld/mail` -> 302 redirect to `https://mail.ifnotus.space`.
- Backend Auth: Direct Dovecot virtual user authentication (`<user>@<domain.tld>` + mailbox password).
- Isolation: Mailbox credentials never authenticate against IFNOTUS API, databases, or hosting panel.

    "iat": 1756369200,
    "jti": "<uuid>",

  * User roles are evaluated on each API call via `CurrentUser` -> database lookup, ensuring role

15. CURRENT TOKEN STORAGE
====================================================================================================
- Current Storage: `localStorage.getItem('access_token')` and `localStorage.getItem('refresh_token')`.
- Frontend Files Involved:
  * `frontend/src/stores/auth.ts`
  * `frontend/src/api/client.ts`
- Vulnerability: Any XSS vulnerability in frontend dependencies can extract both tokens and establish
  long-term persistent unauthorized access.

====================================================================================================
16. COOKIE MIGRATION RECOMMENDATION
====================================================================================================
Recommendation: Migrate from `localStorage` to HttpOnly, SameSite Cookies.

Proposed Cookie Specification:
- Access Token Cookie: `__Host-ifnotus_at`
  * Attributes: `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=1800` (30 mins)
- Refresh Token Cookie: `__Host-ifnotus_rt`
  * Attributes: `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth/refresh; Max-Age=604800` (7 days)
- Scope: `__Host-` prefix enforces host-only scoping (no subdomains, preventing cookie tossing from
  customer tenant subdomains).

====================================================================================================
17. CSRF REQUIREMENTS
====================================================================================================
Upon migrating to HttpOnly cookies, CSRF protection is mandatory for all state-changing endpoints:
- Pattern: Double Submit Cookie or `X-CSRF-Token` header validated against session secret.
- Endpoints Requiring CSRF: All `POST`, `PUT`, `PATCH`, `DELETE` routes under `/api/v1/*`.
- Exclusions: Public webhook callbacks with cryptographic signature validation (e.g. Paystack / MoMo).

====================================================================================================
18. REFRESH-TOKEN ARCHITECTURE
====================================================================================================
- Current State: `POST /api/v1/auth/refresh` accepts a refresh token and issues a new access token.
- Missing Controls:
  * Token family tracking (detecting if an old refresh token is reused).
  * Server-side refresh token invalidation table.
- Recommendation: Store hashed refresh token JTI in Redis / database table. When a refresh token is
  used, rotate the JTI. If a consumed JTI is submitted again, revoke the entire token family immediately.

====================================================================================================
19. SESSION REVOCATION
====================================================================================================
- Current State: `auth.logout()` in frontend simply calls `clearSession()` (removes from `localStorage`).
- Gap: The backend does not maintain a revoked token blacklist; issued JWTs remain valid until `exp`.
- Remediation Plan:
  1. Maintain a Redis/DB table of revoked user session IDs or token issue cutoff timestamp (`tokens_valid_after`).
  2. Invalidate sessions on: Logout, Password change, Password reset, Role downgrade, Account disable,
     and Staff 2FA reset.

23. OTP SECURITY
====================================================================================================
- Evaluated: `backend/app/services/platform/phone_otp.py`.
- Metrics:
  * Length: 6 digits (`secrets.choice("0123456789")` -> cryptographically secure PRNG).
  * TTL: 10 minutes (`OTP_TTL_MINUTES = 10`).
  * Attempt Limit: 5 attempts (`MAX_ATTEMPTS = 5`).
  * Resend Cooldown: 45 seconds (`RESEND_COOLDOWN_SECONDS = 45`).
- Audit Findings:
  * Plaintext OTP codes are never logged to console/disk in production (`dev_show_otp_code()` returns False).
  * Storage is backed by Redis with automatic expiration keys (`KEY_PREFIX = "ifnotus:phone_otp:"`).
  * Verification: PASS.

====================================================================================================
24. OTP RATE LIMITING
====================================================================================================
- Current Limiting:
  * Per-phone cooldown (45s).
  * Max 5 attempts per challenge ID.
- Recommended Hardening:
  * Limit max 3 OTP requests per phone per hour.
  * Limit max 10 OTP requests per IP per hour.
  * Return generic HTTP 200 with delivery message regardless of whether phone exists in database to
    prevent SMS enumeration.

25. MFA IMPLEMENTATION (STAFF TOTP)
====================================================================================================
- Evaluated: `backend/app/services/totp.py` & `backend/app/services/auth.py`.
- Implementation: RFC 6238 TOTP (HMAC-SHA1, 6 digits, 30s period, +/-1 drift window).
- Enforced Roles: `platform_owner`, `platform_admin`, `hosting_operator`, `superadmin`, `admin`, `operator`.
- Audit Finding on Storage:
  * `totp_secret` is stored as base32 in `users.totp_secret`.
  * **Flag**: In remediation, encrypt `totp_secret` at rest using database encryption key (`ENCRYPTION_KEY`).

26. MFA RECOVERY
====================================================================================================
- Current State: No self-service backup recovery codes table.
- Remediation Specification:
  1. Generate 8 single-use 10-character backup recovery codes upon TOTP enrollment.
  2. Store bcrypt hashes of recovery codes in `user_mfa_recovery_codes`.
  3. Recovery Hierarchy:
     - Customer Care / Operator: Reset by Platform Admin.
     - Platform Admin: Reset by Platform Owner.
     - Platform Owner: Must use offline server CLI command (`python scripts/admin_mfa_reset.py`).

31. LOGIN RATE LIMITING & 32. GHANA CGNAT / SHARED-IP FINDINGS
====================================================================================================
- Current Implementation (`backend/app/services/access_control.py`):
  * `CONSECUTIVE_FAIL_LIMIT = 3`
  * `AUTO_UNLOCK_HOURS = 72` (3 days IP ban)
- **CRITICAL FINDING (P0 CRITICAL)**:
  * In Ghana, mobile telecom providers (MTN, Telecel, AT Ghana) assign thousands of mobile subscribers
    to shared Carrier-Grade NAT (CGNAT) gateway IPs.
  * If one user fails 3 logins on mobile data, the entire CGNAT IP block is locked for 72 hours, blocking
    hundreds of legitimate customers in that network area.
- Remediation Requirement:
  1. Decouple IP firewall blocks from individual customer login failures.
  2. Implement progressive backoff per Account (e.g. 1s, 2s, 5s, 15s delay).
  3. Account lockout: 5 failed attempts locks account for 15 minutes (with email unlock option).
  4. IP throttling: 50 failed attempts per IP across ALL accounts triggers temporary 15-minute IP delay.

====================================================================================================
33. ACCESS-CONTROL IP BLOCKING
====================================================================================================
- Current State: `AccessControlService` records attempts in `access_attempts` and writes to `ip_blacklist`.
- Recommendation:
  * Confine automatic IP blocks to volumetric brute-force (>50 failures/minute).
  * Never invoke host-level UFW commands directly from application web request threads.
