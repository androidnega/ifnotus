1. EXECUTIVE CONCLUSION
----------------------------------------------------------------------------------------------------
The IFNOTUS control-plane architecture demonstrates strong foundational security and isolation
mechanisms established across Phases A–Y. Backend authorization is authoritative, tenant data is strictly
sandboxed via `TenantService`, and hosting mutations are routed through `HostingProvider` and ISPConfig 3.

However, several critical control-plane boundaries require formal remediation:
1. Staff Role & Capability Separation: The current 6 roles (`superadmin`, `admin`, `operator`, `viewer`,
   `customer_care`, `customer`) lack clean boundaries between commercial management and technical hosting operations.
2. Web Terminal Surface: `/terminal` currently permits arbitrary shell execution for `superadmin`. While
   audited, web-based command execution represents a critical attack surface and should be restricted strictly
   behind mandatory step-up 2FA and command allowlisting or retired to native SSH.
3. Host File Manager Exposure: Standard staff file management (`/files`) exposes privileged roots (`/srv`, `/var/www`,
   `/var/vmail`) via `admin_storage=True`. Staff file operations must be scoped strictly to individual tenant trees.
4. Route Canonicalization: Obscure login paths (`/admin_1`) and legacy aliases (`/portal/*`, `/staff-login`)
   should be streamlined to standard canonical paths (`/staff/login`, `/login`).

Overall Control-Plane Verdict: SECURE & STABLE; READY FOR FORMAL REMEDIATION SPECIFICATION.

4. ROLE PROBLEMS & 5. PROPOSED ROLE MODEL
----------------------------------------------------------------------------------------------------
1. Ambiguities Identified:
   - `admin` currently possesses `servers:delete` and `apps:write` but cannot manage domain DNS records.
   - `operator` currently possesses `deployments:execute` and `servers:write` but cannot view orders.
   - `customer_care` confirms manual payments but lacks permissions for structured refunds.
2. Proposed 7-Role Capability Hierarchy:
   - `platform_owner` (Superadmin): Staff management, security policy, disaster recovery, terminations.
   - `platform_admin`: Commercial product catalog, plan pricing, coupon campaigns, customer management.
   - `hosting_operator`: Hosting provisioning, domain DNS, SSL certificates, mailboxes, database remediation.
   - `billing_agent`: MoMo payment verification, Paystack reconciliations, invoices, ledger analysis.
   - `support_agent`: Customer support tickets, user profile lookups, password reset assistance.
   - `auditor`: Global read-only compliance inspection.
   - `customer`: Self-service management of subscribed hosting environments.

9. PRIVILEGES TO REMOVE, 10. RESTRICT, AND 11. ADD
----------------------------------------------------------------------------------------------------
1. Privileges to Remove:
   - `admin:servers_delete`: Platform admins should not delete server nodes from inventory.
   - `operator:terminal_execute`: Unrestricted shell execution removed from technical operator.
2. Privileges to Restrict:
   - `terminal:execute`: Restricted strictly to `platform_owner` with mandatory TOTP 2FA challenge.
   - `hosting.terminate`: Restricted to `platform_owner` with explicit `confirm=true` query check.
   - `files:write` across `/srv`: Scoped strictly to specific customer environment trees.
3. Privileges to Add:
   - `billing.manage`: Dedicated capability for manual MoMo payment processing and invoice adjustments.
   - `disaster_recovery.exec`: Capability for initiating offsite backups and restore drills.
   - `providers.manage`: Capability for updating ISPConfig and gateway API credentials.

24. DANGEROUS ROUTES & 25. WEB TERMINAL VERDICT
----------------------------------------------------------------------------------------------------
1. Web Terminal (`/api/v1/terminal/execute`):
   - Findings: Executes shell commands via `asyncio.create_subprocess_shell`. Restricted by regex blacklist
     (`rm -rf /`, fork bombs, `mkfs`) and scopes (`APP`, `HOSTING`, `OPS`).
   - Audit Verdict: Highly sensitive. Retain exclusively for `platform_owner` with mandatory TOTP prompt,
     short session timeout, and complete audit logging.
2. Destructive Database Studio (`/api/v1/databases/studio/query`):
   - Findings: DDL and DROP statements require explicit `confirm_password` verification and emit audit logs.
   - Audit Verdict: Properly gated.
3. Environment Termination (`/api/v1/platform/environments/{id}/terminate`):
   - Findings: Requires `Permission.SYSTEM_ADMIN` and explicit `confirm: bool = Query(default=True)`.
   - Audit Verdict: Properly gated.

26. SERVER FILESYSTEM ACCESS VERDICT & 27. IDOR / CROSS-TENANT DEFENSE
----------------------------------------------------------------------------------------------------
1. Customer File Sandbox (`FileManagerService` with `only_roots`):
   - Verified in `backend/app/routers/v1/customers.py` (line 794): `roots = await TenantService(session).roots_for_environment(customer.id, environment_id)`.
   - Result: Customer A cannot access Customer B's files, product folders (`/srv/apps/quizsnap`), or system roots (`/etc`). Path traversal and symlink escapes are trapped.
2. Staff File Manager (`FileManagerService` with `admin_storage=True`):
   - Findings: Exposes `/srv`, `/var/www`, `/var/vmail`, `/var/backups` to staff users.
   - Remediation: Deprecate arbitrary host-wide file editing. Restrict staff file access to explicit tenant or product application roots.
